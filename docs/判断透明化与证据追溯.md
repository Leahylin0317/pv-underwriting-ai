# 判断透明化与证据追溯

## 用户可以追溯什么

系统结果页和 Markdown 报告都展示从输入到建议结论的路径：

1. 上传材料及材料包完整性检查。
2. OCR 字段、图像检查结果和识别不确定项。
3. 每份材料的审核动作、触发规则、关联 OCR 字段和图片证据。
4. 组件能力与历史气象数据比较，以及数据来源、数值和缺失项。
5. 自动处理步骤的 Provider、模型、状态、耗时和错误信息。
6. 整单汇总顺序、最终建议、参加汇总的规则及其中文解释。

前端通过 `material_reviews.finding_ids` 和 `material_reviews.ocr_field_ids` 将单份材料动作连接到具体识别记录。规则详情来自 `decision.rule_explanations`；原始规则编号同时保留，方便定位配置和代码。

历史案件如果创建于规则说明字段上线之前，读取和人工复核接口会根据原始规则编号补齐中文说明，不要求重跑识别。

## 模型与程序规则的分工

OCR/视觉模型输出文字字段、图片观察、证据描述和参考分数。模型分数尚未经过概率校准，不能解释为某风险实际发生概率。模型也不直接输出整单承保结论。

规则引擎根据材料类别、识别状态、缺失字段、数据完整性和已配置业务规则生成逐项材料动作。决策引擎按以下顺序选择整单建议：

> 建议拒保 → 位置冲突人工复核 → 补充材料 → 其他人工复核 → 建议加费 → 附条件承保 → 建议承保

因此，用户可以检查每一个动作是由哪条规则触发、规则查看了什么证据，以及该动作如何进入整单优先级。处理失败、识别不确定或灾害参数缺失会明确出现在结果中；它们不会被描述为“通过”。

## 规则说明维护

规则中文解释集中在 `backend/app/rules/explanations.py`，每条包括：

- 规则编号和标题。
- 触发条件。
- 对材料动作或后续流程的作用。

新增规则时，应同时增加规则逻辑、规则说明和测试。未登记的规则不会被隐藏：结果中会显示原编号和“规则说明待补充”。`tests/unit/test_rule_explanations.py` 会检查程序中的字面规则编号是否已有说明；风、雹、雪能力比的动态规则编号也有单独测试。

## 当前边界

透明展示说明的是“程序按当前实现为何给出建议”，不代表判断一定正确。高火险行业清单、正式业务规则表、比赛 C 包及 A/B/C 标注真值仍需补齐后，才能核实规则取值并评估真实识别准确率。业务规则发生变化时，应先更新配置和说明，再用标注材料回归验证。
